INTERACTIVE KNOWLEDGE LEXICON

Reusable Project Architecture

A structured blueprint for building an educational lexicon using reusable concept records, educational content, shared layouts, components, styling and automated validation.

Explore. Understand. Experiment.

1. Project Identity

Project: Interactive Knowledge Lexicon (IKL)

Repository: ikl-reusable-architecture-poc

Purpose: Prove that multiple educational concepts can be created using one reusable architecture rather than individually constructed pages.

Initial demonstration concepts: Ping and Process.

Architecture approach: Structured JSON data, Markdown learning content, Jekyll layouts, Liquid components, shared CSS, Python validation and GitHub Actions.

This is an isolated proof of concept. The existing production IKL repository is not being modified or migrated.

4. Architecture and Responsibilities

Structured Data

_data/concepts/

Holds concept identity, subject, description, learning objectives, learning levels and references to educational content.

Educational Content

_learning_content/

Stores Markdown teaching material independently of page design. Content can be expanded into additional learning sections and blocks.

Shared Layout

_layouts/

Defines the common structure of every concept page. New concepts reuse this layout.

Reusable Components

_includes/

Contains smaller reusable page components, beginning with the educational content renderer.

Concept Entry Pages

concepts/

Connect a concept slug to its shared layout. They should not duplicate the full teaching content.

Shared Styling

css/

Holds the visual design system used by all concept pages.

Validation

validation/

Checks structured data, unique identifiers, required fields and content references.

Automated Build

.github/workflows/

Runs automated validation and the Jekyll build through GitHub Actions.

5. Reusable Concept Model

Each concept follows the same general model. The content and data change, while the shared architecture remains consistent.

Step 1 — Concept record

Create a JSON record containing the concept's identity, title, subject, description, learning levels and objectives.

Step 2 — Educational content

Create Markdown content blocks with unique IDs, section information and teaching material.

Step 3 — Concept entry

Create a small Markdown entry page that identifies the concept slug and selects the shared layout.

Step 4 — Shared rendering

The shared layout retrieves the concept record and renders its referenced content blocks.

Step 5 — Shared design

The stylesheet provides a consistent visual experience across all concepts.

6. How a Concept Page Is Generated

  1. Visitor opens a concept URL.
  2. The concept entry page supplies its concept slug.
  3. The shared layout retrieves the matching JSON record.
  4. The layout reads the content block identifiers.
  5. The shared include renders the matching Markdown content.
  6. The stylesheet provides the page appearance.
  7. Jekyll produces the final static HTML page.
Expected result: Ping and Process use the same rendering system while displaying different educational information.

7. Educational Design Principles

Four learning levels

  1. First-grader — simple language and familiar examples.
  2. Beginner — foundational explanations and analogies.
  3. Undergraduate — technical explanations and mechanisms.
  4. Expert — deeper architecture, limitations and connections.

Three learning dimensions

Understand it

Definitions, explanations, analogies and examples.

Learn how it works

Components, mechanisms, architecture and diagrams.

Experience it

Simulations, practical activities and knowledge checks.

Fifteen educational sections

  1. Identity and definition
  2. First-grader explanation
  3. Analogy
  4. Beginner explanation
  5. Technical explanation
  6. Components and architecture
  7. Working mechanism
  8. Interactive simulation
  9. Flowchart and sequence diagram
  10. Practical example
  11. Common mistakes
  12. Limitations and troubleshooting
  13. Connections to other concepts
  14. Assessment
  15. Quick revision

The initial proof of concept demonstrates the first educational content block. It does not implement all fifteen sections yet.

8. Validation and Quality Assurance

The project will use a validation script and automated build checks to reduce structural errors.

Check Purpose
Required fields Ensure every concept has essential information.
Unique IDs Prevent duplicate concept and content identifiers.
Content references Ensure every referenced block exists.
Missing references Detect references to unavailable content.
Jekyll build Confirm the project generates static pages successfully.
Browser inspection Check page appearance, content and navigation in Safari.
The validator and workflow are planned files. Their actual checks and successful execution must be verified before the POC is considered complete.

  • Reusable interactive simulation components.
  • Shared flowchart and sequence-diagram components.
  • Reusable assessment and feedback systems.

Each extension requires its own architectural assessment before implementation.

11. Project Governance and Safeguards

  1. The proof of concept remains separate from the production IKL repository.
  2. Existing working production functionality must be preserved.
  3. No repository restructuring or refactoring without explicit approval.
  4. New concepts should reuse approved shared templates and components.
  5. Test the architecture with Ping and Process before scaling to additional concepts.
  6. Build and validate before considering publication.
  7. GitHub Pages must not be enabled for this POC until the project owner approves.
  8. Approved architecture does not automatically authorize implementation or migration.

12. Proof-of-Concept Success Criteria

The POC will demonstrate its purpose when:

  • Ping and Process are generated from their own records.
  • Both pages use the same layout.
  • Both pages use the same content renderer.
  • Both pages use the same stylesheet.
  • Educational Markdown renders correctly.
  • Concept and content references are validated.
  • Automated Jekyll build completes successfully.
  • Generated pages display correctly in Safari.
  • No changes have been made to the production repository.
The ultimate test is whether a third concept can be added primarily through new data and content files, without rebuilding the shared page architecture.
